# 模板进化指南（回流机制）

> ⚠️ **本文档已于 2026-08-05 归档。**
>
> **归档原因**:本工程(clipboard-manager)是独立子工程,不再是模板母体,
> 不承担「持续进化母体」职责。回流机制是模板母体(`/Users/baijunjie/Documents/infra/tauri-sidecar-template`)
> 专用,母体仓库仍保留本文件的最新版本。本文档保留作为历史轨迹(§1.4)。
>
> 下方内容是归档时的原始版本,不再代表当前工程的工作方式。
>
> **🔴 核心定位**：模板是「持续进化的母体」，不是一次性产物。
> 本文件设计回流机制，让新工程的开发成果回流模板，使模板不断进化、越来越好用。
>
> **模式**：中央模板（本仓库）+ 分支项目（从模板复制起步）+ 回流进化（成果提炼后回流模板）。
>
> **教训**：决策逻辑曾落后 19 个 session 才补救——没有回流机制，模板会停滞。
> 模板不会自动进化，每次回流必须有人主动"抽取提炼 → 去业务化 → 回流"。

## 进化模式图解

```
        ┌─ 新工程A（从模板 v1.0 复制）─┐ 成果提炼回流 ┐
模板工程 ─┤                              ├────────────→│ 模板不断进化（版本递增）
（母体） └─ 新工程B（从模板 v1.1 复制）─┘              │ 越来越好用（CHANGELOG 记录）
    ↑                                                  │
    └──── 每次回流后版本+1 ────────────────────────────┘
```

## 回流触发时机

- **新工程收尾时**：检查"哪些成果该回流"（见下方回流清单）
- **重大成果沉淀时**：开发中发现可复用的通用模式 / 工具 / 踩坑经验

## 回流清单（新工程收尾时逐项检查）

- [ ] **决策逻辑**：新工程开发中是否有新的稳定决策模式？→ 提炼到模板 engineering-principles + decision-cases
- [ ] **工程纪律**：是否发现新的通用工程纪律（不依赖特定业务）？→ 回流到模板 engineering-principles
- [ ] **通用工具/骨架**：是否造了可复用的通用组件/工具/骨架（非业务特有）？→ 回流到模板代码
- [ ] **踩坑经验**：是否有通用可复用的踩坑复盘（非业务特有）？→ 回流到模板 wiki/research/
- [ ] **工程流程**：是否改进了开发流程（收尾清单/review 规范等）？→ 回流到模板 wiki/process/

## 通用性判断标准（回流 vs 不回流）

**核心标准**：这个成果是否依赖"特定业务场景"（如 AI 推理 / 电商图片 / 音频处理）？

- **不依赖**（任何软件开发通用）→ ✅ 回流模板
- **依赖特定业务** → ❌ 不回流（留在分支工程的决策逻辑里）

**判断示例**：
- 修 bug 扩散扫同源路径 → ✅ 通用，回流
- 模型能力是根本（"换更强模型解决能力上限"）→ ❌ AI 推理特有，不回流
- 打包 GUI 实测多轮 → ✅ 通用（任何打包分发），回流
- 进程级拆分优化启动慢 → ⚠️ 通用机制可回流，但具体拆分方案是业务特有

## 回流操作流程

1. **提炼**：从分支工程识别可回流的通用成果
2. **去业务化**：去掉业务专属引用（产品名/业务术语/特定案例），换通用表述或占位
3. **判断通用性**：用上面的标准判断每条是否真通用
4. **PR/合并到模板**：以 PR 或直接 commit 形式回流到本仓库
5. **更新 CHANGELOG**：记录回流（日期 + 来源工程 + 回流内容 + 通用化处理）
6. **版本递增**：回流新增（决策/纪律/工具）→ MINOR +1；修正/小优化 → PATCH +1

## 版本约定（语义化版本）

- `vMAJOR.MINOR.PATCH`
  - **MAJOR**：架构骨架大改（如换框架版本）— **由用户触发**（完成大工程后告知 AI）
  - **MINOR**：回流**新增**（决策逻辑/工程纪律/通用工具/新约束节/新文档）— **AI 主动 bump**
  - **PATCH**：**修正/优化现有内容**（去重、补漏、改错、小优化）— **AI 主动 bump**

### bump 触发与执行（AI 必须遵守）

每次回流操作完成后，AI **必须**立即 bump 版本（不等用户提醒）：

| 操作类型 | bump 到 | 示例 |
|---------|---------|------|
| 回流新经验/新方法论/新文档/新约束节 | MINOR +1 | v1.0.0 → v1.1.0 |
| 修正/去重/优化已有内容（无新增） | PATCH +1 | v1.1.0 → v1.1.1 |
| 大工程完成（用户明确告知） | MAJOR +1 | v1.x.x → v2.0.0 |

**bump 必须同步的位置**（缺一不可，否则版本号是空话）：
1. `wiki/dev/progress.md`「当前状态」段 — **版本号唯一真相源**
2. `CHANGELOG.md` — 新增 `[X.Y.Z] - YYYY-MM-DD` 条目（来源/内容/通用化处理）
3. `wiki/log.md` — 知识库结构变更（新文档/归档/大改）

### 版本号 = 模板与子工程的同步锚点

**子工程在初始化时**记录「基于模板 vX.Y.Z 起步」（写在 `wiki/dev/progress.md` 工程基线条目 + `CHANGELOG.md` 首条）。
**之后判断子工程是否需要同步模板更新**：对照模板当前版本与子工程记录的起步版本，CHANGELOG 里介于两者之间的条目都是该同步的。

```
子工程记录：基于模板 v1.0.0 起步
模板当前：  v1.1.0
→ CHANGELOG [1.1.0] 条目（Stage 5A 回流）= 该同步到子工程的内容
```

> ⚠️ 若回流内容已被子工程独立实现（如 pixel-matrix 自己做了 stage 5A 才回流模板），
> 子工程不需要同步——记录「起步版本」只是为了识别"该看哪些回流条目"，不是强制同步。

## 回流闭环三件套（让机制真正跑起来）

光有"收尾时检查 5 大类"不够——开发时正忙着搞业务，根本不会停下来想"这是不是通用的"。
模板用三件套构成闭环（随复制到子工程，子工程自然就有）：

| 环节 | 文件 | 谁负责 |
|------|------|--------|
| **识别** | `wiki/process/reflux-signals.md`（信号清单）| **AI 主动**——每次干活多扫一眼，命中信号就提示用户 |
| **记录** | `wiki/dev/REFLUX-CANDIDATES.md`（候选池）| AI 提示后用户确认 → 记一条；不靠脑子记 |
| **处理** | `wiki/dev/session-checklist.md` 步骤 5.5 | 收尾时强制过候选池，逐条判定回流/留下/丢弃 |

**核心纪律**：用户专注业务，AI 负责"盯这块通用吗"。靠机制不靠记忆。
