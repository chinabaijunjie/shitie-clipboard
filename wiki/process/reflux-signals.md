# 回流信号清单

> **用途**：AI 在子工程每次干活时，对照本清单扫描"这块是不是回流候选"，发现就**主动提示用户**并记入候选池。
> 用户专注业务，AI 负责"盯这块通用吗"。
>
> 这是回流闭环的「识别」环节。配合 `wiki/dev/REFLUX-CANDIDATES.md`（记录）+
> `session-checklist.md` 回流步骤（处理）构成完整闭环。

---

## 识别信号（看到这些情况 → 可能是回流候选）

> 判断核心：**换个产品 / 换个业务，这块还能用吗？** 能 → 回流候选。

### 🟢 强信号（几乎肯定要回流）

| 信号 | 为什么通用 | 例子 |
|------|-----------|------|
| **解决了一个跟业务无关的技术问题**（框架/平台/库的坑） | 换产品还会踩 | Tauri 2 某个 API 的坑、PyInstaller 打包路径问题、SQLite 并发锁 |
| **造了一个跨产品可复用的代码骨架/组件/工具** | 任何同类应用都要 | API key 加密存储、长任务+进度+取消、文件上传/下载、批量操作模式、表格/列表通用组件 |
| **沉淀了一条新的工程纪律**（不依赖业务） | 任何软件开发适用 | 发现"分散的清理逻辑必须抽 helper"、新的 debug 方法论 |
| **踩了一个通用坑并复盘**（非业务特有） | 换产品还会踩 | async/await 陷阱、依赖版本冲突、CI 配置问题 |

### 🟡 弱信号（值得评估，可能回流部分）

| 信号 | 怎么判断 |
|------|---------|
| **业务功能里藏着通用模式** | 把业务部分剥掉，剩下的机制通用吗？（如"图片生成的进度推送"→ 剥掉图片 = "长任务 SSE 进度"，通用）|
| **改进了开发流程**（收尾清单/review 规范/提交流程） | 流程本身通用 → 回流；流程里引用的业务文件 → 留子工程 |
| **做了配置/设置类功能**（主题/语言/偏好） | 机制通用，具体配置项可能业务特有 |

### 🔴 反信号（看到这些 → 不是回流候选）

| 信号 | 为什么不回流 |
|------|------------|
| 代码里全是业务术语（文生图/角色/订单/商品） | 强业务耦合 |
| 依赖某个特定外部服务的协议（SD API / DALL-E API） | 协议是业务的 |
| 只对这个产品的用户有意义的功能 | 业务专属 |

## AI 主动识别约定（重要）

**每次在子工程干活时，AI 多做一步**：扫一眼当前任务涉及的代码/设计，对照上面的信号清单判断。

发现回流候选时，**主动提示用户**（不等用户问）：

```
💡 回流候选识别

刚才做的 [X] 看起来是通用的（[理由：对应哪个信号]）。
换产品还能用，建议记入 REFLUX-CANDIDATES，做完这轮回流模板。

要我帮你记下来吗？
```

**边界**：
- 只在**确实命中信号**时提示，不要每个改动都问（会变成噪音）
- 用户说"不用" → 尊重，不反复提
- 用户说"记下来" → 写入 `wiki/dev/REFLUX-CANDIDATES.md`

---

## 处理流程（收尾时，见 session-checklist 回流步骤）

1. 读 `wiki/dev/REFLUX-CANDIDATES.md`，逐条过
2. 每条判定：
   - **回流模板** → 去业务化 → PR/commit 到模板仓库 → 更新模板 CHANGELOG（MINOR +1）
   - **留子工程** → 标记原因，不回流（业务特有）
   - **丢弃** → 当时记错了，删掉
3. 处理完的条目标记 ✅，保留记录（追溯用）
