# 工程决策与实践指南

> **本文件是通用工程纪律总入口**——含 22 条适用于任何软件工程（尤其 AI 协作开发）的决策与实践原则。
>
> **文档结构**：
> - §1 通用工程原则（22 条，所有工程工作都必须遵循）

> - §3 决策边界（适用范围）
> - §4 决策流程建议
>
> **来源**：从 ai-audiobook 项目沉淀（20 条从真实开发踩坑提炼，去业务化后的通用纪律）。

## §1 通用工程原则（适用于所有工程决策）

> 这些原则不分技术栈、不分端，是所有工程工作都必须遵循的纪律。

### §1.1 调查先行（含调研必须文档化）

**核心**：任何新阶段 / 新任务启动前，先有完整的调查报告 + 详细规划文档，**不允许直接开工**。调查结果必须立刻持久化到 wiki/，不能只在 AI 的内存里——避免"AI 知道但用户/其他窗口不知道"的信息不对称。

**应用**：
- 启动新阶段 → 先调研，写规划文档
- 大块新工作开始前 → 多代理并行扫描现状
- 任何"涉及多个组件/文件"的改造 → 先有蓝图
- 调研结果立刻持久化到 wiki/
- 决策点用 AskUserQuestion 结构化收集，写入 fix-plan

**反模式**：
- ❌ "直接开始做，遇到问题再说"
- ❌ "上次做过类似的，应该差不多"
- ❌ 调研结果只在 AI 内存里（重启就丢失）
- ❌ 文档散落多处无统一入口（无 wiki/index.md 索引等于不存在）
- ❌ 跨阶段不重新调研，机械套用早期结论

---

### §1.2 严格按规划 + 动态校准（切换节点粒度由方案拆分决定）

**核心**：规划一旦确定就**严格执行（执行过程中不允许中途调整）**，但**每个新"切换节点"开始前必须重新校准规划与现状**。

**"切换节点"的粒度由方案拆分时决定**——可以是阶段切换（粗粒度）、类切换（细粒度，如 A→B→C→D），或任何中间粒度。**拆分方案时明确"哪些节点需要重新校准"，执行时严格按这个粒度走**。

**应用**：
- 执行中：按规划文件走，不擅自调整
- 切换节点（粒度由方案决定）：重新核对资产清单、调研真实状态、更新规划文档
- "重新"是动词——重新跑测试 / 类型检查 / 调用方扫描，看 errors 列表实际变化，**不靠 session 早期内存中的结论直接套用**
- 两个重新调研的理由：① 长上下文中早期结论可能失真 ② 前一节点的代码改动可能无意中影响后一节点的调用方
- 发现新 bug 不边修边补，记 TODO 等专项修

**反模式**：
- ❌ 机械执行规划，遇到脱节也不调整（导致大量返工）
- ❌ 随意调整规划，没有稳定基准（失去规划的意义）
- ❌ 切换节点不重新调研（早期结论可能已过时）
- ❌ "上一节点已经做过类似分析"，跳过调研直接开干

---

### §1.3 文档是开发依赖（不是事后整理）+ 文档治理

**核心**：文档与代码同步维护，**每次改动同步更新进度/链接/交叉引用**。文档不是事后整理，是开发过程中的依赖。

**应用**：
- 新增文档时（必须）：更新 wiki/index.md 加索引
- 完成阶段时（必须）：更新 progress.md
- 重要决策时（必须）：更新 plan.md 顶部注释

**反模式**：
- ❌ 代码改完了再补文档（往往忘记）
- ❌ 文档放在个人目录（重启后找不到）
- ❌ 文档之间无交叉引用（孤立）
- ❌ 新文档不更新 index.md（等于不存在）

**文档定位分层（3 层）**：

| 层级 | 定位 | 内容 | 例 |
|------|------|------|----|
| **入口层** | 规则手册 + 知识库入口 | 启动必读、核心原则、知识查询决策树 | `AGENTS.md` / `CLAUDE.md`（保持精简，不存开发细节）|
| **内容层** | 知识仓库 | 架构/设计/模块/进度/TODO/硬约束/决策原则 | `wiki/`（团队可读，随项目分发）|
| **元层** | 个人分析 | 流水账/决策逻辑/工作风格分析 | 个人目录（不进 git，不进 wiki）|

- 入口层文件是入口，**不存开发任务/进度/设计/模块细节** → 这些归 wiki 内容层
- wiki/index.md 是内容层"门面"，统管全局

**index.md 统管全局**：wiki/index.md 作为知识库"门面"，必须让 AI **深刻了解到它所拥有的所有内容**——场景驱动速查表 + 资源总览 + 分类导航。**内容丰富但 AI 不知道有什么 = 隐身**。

**幽灵引用必须立项**：代码或文档里引用 `TODO-XXX` / `vX.Y` / `wiki/xxx.md` 时，**被引用的对象必须真实存在**——TODO 必须先在 wiki/dev/TODO.md 立项、版本号必须已 tag、文档必须已建立。幽灵引用 = 给读者挖坑。

### §1.4 主动暴露错误（不掩盖，保留历史轨迹）

**核心**：发现自己的产出（文档/代码/方案）有错时，**主动暴露并修正**，不掩盖错误也不删掉重建——保留历史轨迹让后续读者理解演进过程。错误成为学习素材而非耻辱。

**应用**：
- 发现自己之前写的设计/方案/文档有错：改 + 加「⚠️ 重要更正」段，不删原文
- 测试/代码暴露出文档与现实不符：修正文档（不掩盖）
- 写入大文件前逐行核对完整内容（避免手滑改无关代码）

**被用户指出错误后的反思纪律**（5 步流程，**不只修当前问题，要防同类再犯**）：

1. **立刻承认**（不掩饰 / 不辩解）—— 明说"这是遗漏"，承认 gap 真实存在
2. **主动找根因**—— 为什么规则没覆盖？是入口规则漏 / engineering-principles 原则漏 / 流程漏？
3. **主动扩散找同类遗漏**—— grep 类似关键字，扫描其他文档是否有同类问题。**不只修当前一个文件**。**为什么必须扩散**：当你突然发现一个地方出现问题时，**极可能这个问题已经有很多处了**——它通常不是孤例，而是某个规则/流程缺失导致的全局性问题
4. **反思预防方案并落地**—— 反思"要怎么解决类似问题"，把方案落到工程文档。**反思了就要改正**——反思不落地 = 白反思，同类问题必然再犯
5. **跑测试 + 验证补救无回归**

**反模式**：
- ❌ 静默修改，不留修正记录
- ❌ 删掉原文档重建（丢失历史）
- ❌ 推卸责任（"那是上一阶段写的"）
- ❌ 被指出错误后只修当前一个文件（不扩散扫描）
- ❌ 被指出错误后不加预防规则（同样错误必然再犯）

### §1.5 实测发现为准（不靠内存中的旧结论）

**核心**：决策基于**当前的真实状态**，不是基于"上次的状态"或"内存中的结论"。哪怕已经读过相关代码，关键决策前也要重新跑测试 / 重新调研 / 重新验证。

**通用准则**：**任何文档和执行计划，拿到手的第一件事，就是依据当前工程状态对其中的关键点进行验证，验证通过后才可以开工。** 那份执行计划只是本次任务的开端，**还不是执行标准**——只有亲自确认过的，才是执行标准。

**应用**：
- 修 bug 前：重新跑测试看实际错误信息
- 重构前：重新调研函数调用方
- 跨阶段：重新跑类型检查 / lint 看 errors 列表
- **拿到执行计划/规划文档**：开工前先按当前工程状态验证关键点（不是免检金牌）
- **轻信注释声称的「能力 / 支持范围」**：注释描述「能做到什么」必须实测验证，尤其兼容性 / 格式支持 / 「与 X 对齐」类注释

**打包/分发场景的实测纪律**：
- **冒烟测试 ≠ 真实用户验证**：自动化测试覆盖代码逻辑，但覆盖不到「进程生命周期 / 操作系统交互 / 真实用户操作序列」。**打包分发类工作(tauri build 产出 .app/.exe)必须 GUI 实测**
- **单轮 GUI 实测不够，需多轮递进**：每轮修复会改变行为，暴露此前修不到的盲区。**GUI 实测是迭代验证循环（修一轮 → 实测一轮 → 再修）**
- **打包性能结论必须用打包产物实测**：开发态性能数据会严重误导打包场景——打包后可能慢 10-25 倍
- **重打包后必须验证 binary 含新代码**：打包链路每步都可能静默失败，重打包后确认产物确实含新代码(Rust 检查 cargo 重新编译了目标 crate)

### §1.6 测试保护优先于重构（无测试不重构）

**核心**：重构无测试保护的代码 = 把稳定性当赌注。重构前必须先补测试，让测试成为重构的安全网。

**应用**：
- 重构前调研：识别哪些函数无测试保护
- 决策：选"补测试 + 拆"（不是"只拆有测试的"或"全拆不补测试"）
- 流程：补测试 → 拆 → 验证（每函数 2 commits：test + refactor）

**反模式**：
- ❌ 直接拆无测试的代码（赌稳定性）
- ❌ 只拆有测试的，没测试的留作技术债
- ❌ 为了通过测试用 hack 方式（破坏稳定性）

---

### §1.7 范围严格收敛（衍生问题不混入当前分支）

**核心**：每个 Tier / 分支有严格范围。review 期间发现的衍生改进**不混入当前分支**，记入 TODO 等独立 Tier 处理。分支范围严格 → git log 清晰。

**应用**：
- 当前分支范围严格收敛
- review 衍生问题（不阻塞 merge）→ 记 TODO 独立 Tier
- 从 master 重新拆任务，每个独立 Tier 范围清晰

**衍生问题分流三态**：

| 分流 | 处理 | 判断标准 |
|------|------|---------|
| **代码改动**（影响测试/行为/契约）| 必须立项 TODO + 独立 Tier | 改动代码 |
| **文档补充**（README/注释/typo）| 直接 commit，不必立项 | 不动代码 |
| **想法/灵感**（不是 bug）| 进想法池文档，不进 TODO | 未来可能做 |

**小问题当场修**：明确范围的小 bug（根因清晰，改动 < 50 行）/ 体验优化 → **当场直接修，不记 TODO**。

**拆分判断标准**（什么情况下接受"拆到下次会话做"）：
- **上下文充足 + 任务不难时，当场迅速解决**
- **只有当能证明"为什么不能本次做"时，才接受拆分**。拆分建议必须含三要素：① 具体工作量拆解 ② 为什么本次做不了 ③ 下次怎么接续

---

### §1.8 拒绝二分法（融合方案：目标 + 节奏解耦）

**核心**：工程决策时拒绝"理想架构 vs 风险最小"二分法。正确做法是把架构目标和执行节奏解耦——目标是彻底的（架构合理），节奏是渐进的（风险最小）。**风险不是被消除，而是被分摊到每一步**。

**反模式**：
- ❌ AI 主动给二分法（"彻底 vs 保守"，让用户二选一）
- ❌ 用 hack 方式让测试通过伪装风险最小

---

### §1.9 致命缺陷排除法

**核心**：选方案时，先识别每个选项的"致命缺陷"（会破坏稳定性 / 引入悬挂状态 / 规则脆弱），有致命缺陷的方案直接出局。**不基于"工作量小"选方案**。

**反模式**：
- ❌ "工作量小就能选"（短期成本是最低优先级）
- ❌ 不识别致命缺陷就选"推荐项"

---

### §1.10 不盲信既有方案（errata 作为补丁层）

**核心**：接手他人写的方案 / 跨会话交接的方案时，**先逐节验证方案的细节准确性**，发现偏差建立 errata（勘误）文档作为补丁层，**不直接修改原方案**（保留原方案作为蓝图的历史价值）。

**反模式**：
- ❌ 直接执行方案，遇错再回头改
- ❌ 直接修改原方案，丢失历史轨迹
- ❌ 全部重写方案（浪费原作者的工作）
- ❌ 盲信 errata（勘误文档也会有过时之处）
- ❌ **盲信网搜通用结论直接全量改造**：即使是"多个资料一致说的通用结论"（如网搜都说某方式更快），也不能直接全量改造——通用结论常基于普通场景，自己的特殊场景（重依赖 / 特殊架构）可能完全相反。**采纳通用结论前必须先小规模 spike 实测验证**（尤其涉及重依赖 / 打包配置 / 性能优化方向时）。只有"会引发大改造 / 影响架构"的通用结论才需要 spike。

---

### §1.11 关键决策 spot check（5 类决策不擅自执行）

**核心**：大部分决策可以在已确立原则内自主推进，但**5 类关键决策即使有授权也应该 spot check**（"我打算这么做，理由是 X，要不要看一下？"）。

**5 类关键决策**：
1. **架构变更**（模块拆分 / 接口重新设计 / 数据模型调整）
2. **跨模块影响**（修改被多处调用的核心 API / 公共组件）
3. **不可逆操作**（删除数据 / 重置状态 / 删除公共工具函数）
4. **新依赖引入**（添加第三方库 / 锁定版本变更）
5. **安全相关**（认证 / 授权 / 加密 / 文件 IO）

**反模式**：
- ❌ 关键决策也完全自主执行（架构变更/不可逆操作的风险无法被原则兜底）
- ❌ 把常规决策也当成关键决策频繁 spot check（破坏执行节奏）

---

### §1.12 改动生效验证（改完代码主动让运行中的服务加载新代码）

**核心**：代码改完 ≠ 改动生效。改完代码后必须**主动确认运行中的服务加载了新代码**(重启服务 / 确认前端热更新生效 / 重跑 tauri dev),**不等用户提醒**。

**应用**（改完代码后的自检）：
- **改了前端代码**(`src/*.ts/.tsx`)：dev server 通常热更新自动生效,但**明确告知用户"前端改动需刷新浏览器"**
- **改了 Rust 层 / 原生层**(`src-tauri/`)：需要重新 `tauri dev`(用户侧动作),明确告知
- **报告完成前必做**：代码改完 + 服务加载新代码 + 类型检查通过,三者缺一才算"没做完"。报告"已修复"但服务还在跑旧代码 = 谎报

**反模式**：
- ❌ 改完代码直接报告"修复完成",但运行中的进程还在跑旧代码(用户一测发现没生效)
- ❌ 让用户判断改了哪层、要不要重启（用户不该承担这个认知负担）

---

### §1.13 跨模块改造的原子性（类型推广/契约变更不拆 commit）

**核心**：跨模块的类型推广 / 接口契约变更必须**原子改造**——所有受影响的文件一起改 + 一起 commit，不能按"先 A 模块再 B 模块"拆 commit。拆开必有类型检查中间报错状态。

**应用**：
- 跨模块类型推广（Literal / TypedDict / Protocol 多模块共享）→ 所有引用方一起改
- 接口契约变更（API schema / Service signature）→ 所有 caller 一起改
- 跨文件 rename → 一起改

**反模式**：
- ❌ 按"先源头再下游"拆 commit（类型检查中间状态必破）
- ❌ 用 `# type: ignore` / `noqa` 临时绕过中间状态

---

### §1.14 质量优先于体验

**核心**：当**核心功能质量**与**用户体验/进度反馈**冲突时，保质量、放弃体验。延伸后端决策优先级到新维度——**质量 > 体验**。偏好**真实数据**而非**虚假的百分比进度**。

**应用**：
- 进度展示 → 用真实产出数据（已生成/已处理量/速率），不编造平滑百分比
- 体验优化不能以损失核心功能质量为代价

**反模式**：
- ❌ 给用户虚假的进度条（百分比平滑增长，实际后端无对应真实状态）

---

### §1.15 实测排查排除错误假设（A/B 对照锁定根因）

**核心**：排查复杂 bug 时，静态分析（读代码推理）容易给出**看似合理但错误**的根因假设。正确做法是：每个假设都用**实测/数据**验证、排除不成立的，最后用 **A/B 对照实验**（只改变一个变量）锁定真根因，**再修复**。

**执行要点**：
1. 静态分析得出假设后，**先不修复**，先设计验证实验
2. 验证实验从**最易获取的数据**开始（DB 时间戳 / 日志 / 配置对比）
3. 多个假设全部被推翻时，用 **A/B 对照实验**（只改一个变量，对比结果）
4. 锁定根因后再修复，修复后重新跑 A/B 确认

**反模式**：
- ❌ 静态分析得出假设 → 直接修复（可能修了错的，浪费一轮）
- ❌ 实测验证时改变多个变量（无法确定是哪个变量起作用）

---

### §1.16 开发前调研 + 计划固化（重大任务决策与执行分家）

**核心**：对**重大任务**（L 工作量 / 跨模块 / 涉及关键决策），当前会话只做调研 + 产出可执行计划文档，下次会话专注执行不重议决策。**本质动机是让大任务有一个干净的起点**。

**计划文档必含要素**：
- 现状盘点（常发现"基础设施 80% 已就绪"从而降低工作量预估）
- 关键决策固化 → 下次会话不重议
- 坑点清单（易错点提前标注）
- commit 拆解（每个 commit 改什么 + 测什么）
- 启动咒语（下次会话直接复制）

**应用场景**：任务工作量 L（半天+）/ 跨模块 / 涉及关键决策（架构/新依赖）。

**反模式**：
- ❌ S-M 工作量也走"调研+计划"流程（过度规划，简单任务直接执行）
- ❌ 计划文档只列步骤不列决策（下次会话还得重新讨论）

---

### §1.17 修 bug 主动扩散扫描所有同源路径

**核心**：当一个 bug 暴露，修复**不能只改当前报错的那一个调用点**，必须主动枚举所有走同一逻辑 / 同一资源的其他路径。分散多处的同类清理逻辑必然漏，应抽 helper 单点维护。元层规律：**一次修复往往只修了一个路径，同类问题的其他路径是下一轮实测的必然暴露点**。

**应用**：
- bug 暴露时主动 grep / 扫描所有走同一逻辑的调用点
- 同类清理逻辑分散多处 → 抽 helper 函数集中单点维护，不 copy-paste 散落
- 修 bug 时顺带核对同类资源路径是否都覆盖

**反模式**：
- ❌ 只改当前报错的调用点，不查同类路径（反复实测会暴露第二层、第三层同类 bug）
- ❌ 同类清理逻辑 copy-paste 散落多处（必然漏一处）

---

### §1.18 功能完整不留半成品（选定的事一次闭环）

**核心**：**选定要做的事，就一次做完形成闭环**，不接受"本次只做一半、剩下的下次再说"式的半成品（除非有 §1.7 拆分边界的充分理由）。与范围收敛（§1.7）不矛盾：收敛的是"做哪些"，完整的是"选定范围内的功能闭环"。

**应用**：
- 选定的功能范围一次做完，不拆成多次
- 多个相关决策全选完整方案（不做"先做基础版留扩展点下次加"）

**反模式**：
- ❌ "本次先做核心，剩下的留扩展点下次加"（半成品，破坏功能闭环）

---

### §1.19 昂贵验证资源高效调度

**核心**：昂贵验证资源（打包 / 长跑集成测试 / 端到端联调 / 真实模型推理）要**攒批高效利用**，不消耗在反复单点测上；当 AI 陷入"打包 → 验证 → 又发现问题 → 再打包"的单点循环时，**主动叫停**，先理清全局再推进。

**应用**：
- AI 陷入"打包 → 验证 → 又发现问题 → 再打包"单点循环 → 主动叫停，先理清所有问题
- 实测成本高时 → 先列清所有未修问题，攒齐集中修 + 集中测，不发现一个测一次

**反模式**：
- ❌ AI 在昂贵循环里空转不干预（浪费十几分钟 / 半小时一次次）
- ❌ 发现一个问题就测一次（昂贵资源低效利用）

---

### §1.20 跨工程隔离（无关大改动不在当前工程动刀）

**核心**：当任务与当前工程无关、或可能引入污染（如移植一个工具 / 引入实验性大依赖），应**隔离到独立工程**做——只产出提示词 + 计划文档，拿去新工程执行，验证后再接入。**否决"收到任务就在当前工程直接实现"的本能**。

**应用**：
- 任务与当前产品无关（如开发通用工具 / 模板）→ 独立工程做
- 改动可能污染当前代码库（如引入实验性大依赖）→ 独立工程验证后再接入
- 收到无关任务时，主动提议"这适合独立工程，我先出计划 + 提示词"

**反模式**：
- ❌ 收到无关任务直接在当前工程实现（污染代码库，耦合，未来难复用）
- ❌ 不产出可执行计划文档（用户拿不到新工程就开不了工）

---

### §1.21 模块化 · 高内聚低耦合（大模型开发的复杂度控制根基）

**核心**：所有代码必须按职责拆成独立模块——**模块边界清晰、单一职责、对外暴露最小接口、模块间单向依赖不互相渗透**。这条纪律在大模型开发时代具有**战略级优先级**:AI 写代码速度快,但速度快会放大耦合风险(一次性生成大量相互引用的代码,边界一旦模糊就难以回收)。模块化让每个单元**独立可理解、可排查、可单独修改**,是保证 AI 长期可控的复杂度控制根基。

**判据**(判断是否符合模块化):
- 能否用一句话说清一个模块的职责?说不清 → 职责不清,要拆
- 改 A 模块是否必须同时改 B 模块的内部?是 → 耦合,要解
- 一个模块的修改是否会引发非预期的连锁反应?是 → 边界漏了
- 新人(或新会话的 AI)能否只读一个模块就理解它,不需要同时读三个?

**应用**：
- 新功能 → 先定模块边界(职责划分),再写代码;不要边写边长出边界
- 跨平台代码(如 M1 macOS / M3 Windows)→ 平台特定逻辑与平台无关逻辑分层隔离,
  平台无关层(存储/数据模型/业务规则)不感知平台差异
- 公共能力(DB / 配置 / 错误处理)→ 独立模块,被依赖,不反向依赖业务
- 模块对外只暴露最小接口(pub items 精简),内部实现细节不外泄
- 单文件 200-400 行典型、800 行上限(见 AGENTS §8);超出先想拆模块不是拆函数

**反模式**：
- ❌ 「上帝模块」:一个模块干多件事(既监听又存储又 UI),改一处动全身
- ❌ 环形依赖:A 依赖 B,B 又依赖 A
- ❌ 跨模块直接操作对方内部状态(应走对方暴露的接口)
- ❌ 平台特定代码散落在通用逻辑里(`if macos` 满天飞,而非集中在平台层)
- ❌ 为了「快」先写成一坨,想着「以后再拆」(以后不会拆,耦合只会加深)

> 📌 **与 §1.13 的关系**:§1.13 讲跨模块改造要**原子提交**(不拆 commit);本条讲怎么**设计**模块边界。先有清晰的边界(本条),改造时才能干净地原子提交(§1.13)。

---

### §1.22 随写随测（测试与代码同步,闭环才算完成）

**核心**：完成一块代码,对应的单元测试**必须同步编写**——「写完代码 + 写完测试 + 测完通过」是一个完整闭环,缺一不可。**绝不积压到全部代码写完才补测试**。在大模型开发场景下这条尤其关键:AI 一次生成大量代码后再测,出错时定位成本极高(不知道是哪一块引入的问题);随写随测把缺陷锁定在最小范围内,出错立刻知道是刚写的那块。

**闭环判据**(一块代码「完成」的标准):
- 代码写完 + 对应单测写完 + `cargo test` / `npm test` 跑绿 = 这块完成
- 代码写完但没测试 = **不算完成**,不能进下一块、不能 commit
- 测试写了但没跑 / 跑红 = **不算完成**

**应用**：
- 每完成一个模块/函数,立即补单测并跑绿,再进下一块
- 可测的纯逻辑(数据转换 / 决策判断 / 算法)必须 100% 单测覆盖
- 不好测的系统交互(系统剪贴板 / 网络 / 文件系统 / GUI)→ 把**可测的决策逻辑抽成纯函数**,纯函数单测覆盖;系统交互本身靠集成测试/手动验证
  - 例:剪贴板 handler 的「是否捕获」「是否入库」抽成 `should_capture()` / `is_worth_storing()` 纯函数单测;真正的系统剪贴板读写靠实测
- 测试用内存 DB / 临时文件 / mock,不依赖真实环境(`init_db_in_memory()` 而非真实 db 文件)
- commit 前必跑全量测试,确保没破坏既有基线(回归)

**反模式**：
- ❌ 先写完所有代码再「统一补测试」(积压,出错来不及定位)
- ❌ 代码写完就算「完成」,测试以后再说(永远不会有「以后」)
- ❌ 系统 IO 和业务逻辑混在一起无法单测(应抽纯函数)
- ❌ 测试依赖真实环境(真实 DB 文件 / 真实网络),别人跑不动
- ❌ 写了测试但不跑 / 跑红了不管就 commit

> 📌 **与 §1.21 的关系**:§1.21 讲模块边界设计(让代码可测);本条讲必须实际去测。模块化(§1.21)让「随写随测」成为可能——职责单一的纯函数才好测;反过来,随写随测(本条)会倒逼模块化(为了可测而抽纯函数)。

## §3 决策边界（适用范围）

### ✅ 适用

所有**工程决策**：
- 前端代码（`src/` 全部）
- 后端代码（`backend/` + `src-tauri/` + `scripts/`）
- 跨端协作（API 契约 / 数据流 / 错误处理）
- 工程流程（测试策略 / 重构边界 / 依赖引入 / 文档维护 / git 操作）

### ❌ 不适用

- **纯产品功能决策**（功能范围 / 用户体验 / 交互流程）
- **纯视觉设计决策**（配色 / 字体 / 视觉风格）
- **纯文档措辞决策**（文字表述）— 无技术风险

---

## §4 决策流程建议

遇到工程决策时：

1. **识别决策类型**（bug 修复 / 重构 / 新功能 / 依赖引入 / 跨端协作 / 文档维护 / git 操作）
2. **查 §1 通用原则**——所有决策都适用
3. **识别是否属于 §1.11 关键决策**（5 类）——是则 spot check
4. **查 §2 历史案例**是否有类似情境
5. **如果都有**：按原则 + 案例决策
6. **如果都没有**（新场景）：按 §1 通用原则决策，**决策后追加到 [[decision-cases]]**
