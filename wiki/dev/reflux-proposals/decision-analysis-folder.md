# 回流提案:决策分析文件夹纳入模板

> 子工程(clipboard-manager)产出,请带到母工程(tauri-sidecar-template)会话执行合并。
> 本文档自包含 —— 母工程读了就能直接执行,不需要了解子工程业务细节。

---

## ① 项目背景(为什么回流)

### 问题

模板母工程(tauri-sidecar-template)目前**没有「决策分析」文件夹**。子工程开发过程中想记录「开发流水账 + 决策模式提炼」(对应 engineering-principles §1.3「元层定位」—— 流水账/决策逻辑/工作风格分析归此,不进 git 不进 wiki),只能:

- 从**其他工程**(ai-audiobook / pixel-matrix)手动复制「决策分析」文件夹过来
- 复制来的 README 带**旧工程的残留信息**(旧工程名、旧阶段、旧 commit 列表、旧血缘说明),要手动清理
- 每个子工程重复这个「复制 + 清理」动作

### 解决

把「决策分析」文件夹**纳入母工程的 Git 管理**,作为模板资产的一部分。这样:

- 从母工程创建的任何子工程,**天然就带有「决策分析」文件夹 + 通用 README**
- README 是**通用流水账规则手册**(无任何具体工程信息),子工程的大模型读了就能直接整理流水账
- 通过 `init-project.sh` 的改动,保证**子工程的「决策分析」不进 git**(子工程元层 §1.3 不入 git),而**母工程的进 git**(模板资产)

### 权限区分(核心设计)

| | 母工程(tauri-sidecar-template) | 子工程(如 clipboard-manager) |
|---|---|---|
| 「决策分析」是否进 git | ✅ **进 git**(模板资产,所有人 clone 就有) | ❌ **不进 git**(子工程元层,§1.3) |
| 实现方式 | 母工程 `.gitignore` **不**排除 `决策分析/` | `init-project.sh` 复制后往子工程 `.gitignore` **追加** `决策分析/` |

> 这样母工程的 README(通用规则)被版本管理、随模板演进;子工程复制后自动 ignore,子工程写的具体流水账(个人元层)留在本地不入 git。

## 📝 录入规则（每次会话结束后必读）

> **触发场景**：用户说"把这次会话整理成流水账"/"录入决策分析"/"加一次会话" 等类似指令时，按本规则执行。
>
> **谁需要读**：未来任何接手"录入"任务的窗口（Claude Code / ZCode / 其他智能体）。
> **目的**：保证录入内容风格一致、质量稳定，让决策模式的提炼始终有可信的原始素材。

### 1. 何时录入

| 触发条件 | 是否录入 |
|---------|---------|
| 用户**明确要求**"整理成流水账" | ✅ 必须录入 |
| 会话包含**重大决策点**（架构选择、流程调整、错误处理等）但用户未明示 | ⚠️ 建议主动询问"要不要录入决策分析" |
| 会话是**纯执行**（无决策，按既有规划走） | ❌ 不录入（避免流水账膨胀） |
| 会话是**纯调试**（修单个 bug，无模式提炼价值） | ❌ 不录入 |

### 2. 录入前准备（必做）

```
1. 确定本次会话的编号（递增：01, 02, 03...）
2. 确定会话日期（用于文件名和顶部时间）
3. 通读既有流水账（必读，了解风格）
   - 若是本工程第一篇，参考下方「流水账单条记录格式」和「文件结构模板」
   - 若已有流水账，至少读最近 1-2 篇的前 100 行，对齐风格
4. 回顾本次会话的决策点（哪些是用户做的、哪些是 AI 自动判断的）
```

> **注**：若使用 Claude Code，可从 `~/.claude/projects/<工程路径编码>/` 提取 session ID；
> 若使用 ZCode，按对话轮估算即可，文件名用日期作为兜底标识。

### 3. 录入步骤（4 步走）

#### 步骤 1：新建流水账文件

**文件命名**：
- 编号：递增（01, 02, 03...）
- 标识：Claude Code 用 session ID 前 8 位；ZCode 用日期（如 `2026-08-07-zcode`）
- 格式：`{编号}-session-{标识}.md`
- 示例：`01-session-2026-08-07-zcode.md`

**文件结构**（严格按既有流水账风格）：
```markdown
# 流水账 {编号} — Session {标识}（{会话主题简述}）

> **会话时间**：{年-月} {日期}，{HH:MM} - {HH:MM}（约 {N} 小时）
> **会话主题**：{一句话主题}
> **会话性质**：{本次会话的关键性质，如"规划制定"或"主力执行"或"调研分析"}
> **工具**：{Claude Code / ZCode / 其他}

---

## {HH:MM} - {简短标题}

**你说**：
> {用户原话，含口语/语气}

**AI 给的选项/分析**：
- 选项 A：...
- 选项 B：...

**你的决策**：选 X

**决策原因**：{用户原话或从对话推断}

**后续影响**：{含 commit hash}

---

... (按时间线重复多个决策节点) ...

---

## 本次会话总结

**性质**：...
**核心动作**：1. ... 2. ... 3. ...
**用户表现出的偏好**：与既有模式的一致性 + 新观察
**与既有模式的演进**：既有模式如何演进
**与后续会话的关联**：...

---

## {N} 个 commit 速查

| commit | 类型 | 内容 |
|--------|------|------|
| {hash} | {type} | {简述} |
```

#### 步骤 2：追加决策模式（如有新模式，需积累后做）

> **首版决策模式文档何时建立**：建议积累 3-5 个有决策点的会话后再做首版提炼（避免单次观察过早抽象）。
> 文件命名：`decision-patterns.md`（首版）或按主题组织的 `决策逻辑v1.0.md`。

**判断**：本次会话是否观察到**新的稳定模式**（不是单次行为，是跨场景的可重复偏好）？

**操作**：
- ✅ **有新模式**（已有模式文档时）：在 `decision-patterns.md` 末尾追加（编号继续递增）
- ✅ **既有模式有新证据**：在对应模式的「证据」段落追加新会话节点（标注 session-N + 时间）
- ❌ **无新模式 / 还没首版文档**：跳过此步，只记流水账

**模式字段结构**（必含）：
```markdown
## 模式 {N}：{简短标签} — {一句话副标题}

**核心描述**：...

**证据**：
- session-N HH:MM 决策 X：{引用对话} → {产出/commit}

**应用场景**：...
**反模式**：❌ ...
**价值**：...

**与既有模式 X 的关系**：{协同/精细化/独立}
```

**重要**：
- 每条新模式必须引用**至少 1 个**具体会话节点（不能空谈）
- 标注**样本量**（基于几次会话观察）——单次观察的模式要标"建议再观察 1-2 次再固化"
- 不删既有模式，**只追加**

#### 步骤 3：更新本 README

必改 2 处：

1. **「📌 当前状态」段**：会话数 +1，更新流水账列表
2. **「目录结构」表**：加一行新流水账

如本次会话新增了决策模式或建立了首版模式文档，还要更新：
3. **「📌 当前状态」段**的决策模式版本
4. **「目录结构」表**的决策模式文件行

#### 步骤 4：让用户审阅（推荐）

写完后**给用户看摘要**：
- 新建文件名 + 行数
- 决策模式新增了几条 / 补充了几条（若有）
- README 更新了哪些段

用户确认前不要 commit（注：本目录不入 git，所谓"commit"指工作完成的确认）。

### 4. 质量底线（必检）

- [ ] **保留用户原话**（含口语/语气/错别字）——不要"修正"成书面语
- [ ] **commit hash 全部标注**（每个决策的后续影响必含 hash）
- [ ] **不写事后诸葛**——流水账是原始记录，模式提炼归决策模式文档
- [ ] **不删既有文件**——只追加，不重写（除非用户明确要求"重写一版"）
- [ ] **主动暴露错误**——如果本次会话 AI 自己写错了什么，必须记录「⚠️ 重要更正」类段落，不掩盖
- [ ] **区分"用户决策" vs "AI 自动判断"**——明确标注每个决策是用户做的还是 AI 做的
- [ ] **文件命名零冲突**——编号递增 + 标识唯一，不允许覆盖

### 5. 反模式（不要做）

- ❌ 把流水账写成"会话总结报告"（流水账是按时间线展开，不是按主题归纳）
- ❌ 把决策模式从流水账里"提炼"成全新的抽象（应基于具体对话节点）
- ❌ 修改历史流水账（那是历史快照，保留原样）
- ❌ 把决策分析文件同步到 `wiki/`（违反 engineering-principles §1.3「工程文档 vs 个人分析严格分离」）
- ❌ 录入纯执行/纯调试的会话（无模式提炼价值）
- ❌ 重写既有决策模式文档（追加而非重写，保留演进轨迹）
- ❌ 单次观察就固化为模式（标"候选"，等 2-3 次跨场景验证后再固化）

### 6. 边界情况处理

| 场景 | 处理方式 |
|------|---------|
| 用户说"重写一版决策模式" | 询问是否真的要重写，还是追加。默认追加（保留演进轨迹） |
| 会话太长（>8 小时或 >200 对话轮）| 拆成多个流水账文件（如 03a / 03b），但同一会话标识 |
| 会话涉及多个项目 | 只录入本项目相关部分，其他项目略过 |
| 会话无明显决策点 | 不录入，告诉用户"本次会话是纯执行，无决策模式提炼价值" |
| 会话标识找不到 | 用日期作为文件名（如 `03-session-2026-08-07.md`），并在文件顶部说明 |
| 既有模式被本次会话**推翻** | 不删原模式，在原模式后追加「⚠️ 反例（session-N）」段，说明边界 |

### 改动 3:`scripts/init-project.sh` —— 复制后往子工程 `.gitignore` 追加 `决策分析/`

在 `init-project.sh` 的 **rsync 复制之后、git init 之前**,加一段:往子工程的 `.gitignore` 追加「决策分析」排除规则。

**插入位置**:`# 3. git init` 注释块**之前**(约当前第 214 行 `# 3. git init` 之前)。

**要插入的代码**:

```bash
# ============================================================
# 2.5 子工程元层排除：决策分析（母工程进 git，子工程不进）
# ============================================================
# 决策分析/ 是用户的个人开发流水账（§1.3 元层，不入 git）。
# 母工程把它作为模板资产进 git（含通用 README）；子工程通过这里追加 .gitignore 排除。
# 子工程自己写的流水账保留在本地，不污染子工程仓库。
DECISION_ANALYSIS_ENTRY="
# 决策分析（个人开发流水账，§1.3 元层，不入 git）
决策分析/
"
if ! grep -q "决策分析/" "$TARGET_DIR/.gitignore" 2>/dev/null; then
    printf '%s\n' "$DECISION_ANALYSIS_ENTRY" >> "$TARGET_DIR/.gitignore"
    ok "已往子工程 .gitignore 追加「决策分析/」排除（子工程元层不入 git）"
fi
```

> 说明:
> - 用 `grep -q` 先判断,避免重复追加（幂等,init 脚本重跑不会重复加）
> - 追加到 `.gitignore` 末尾,带注释说明原因
> - 放在 git init 之前,这样 `git add -A` 时「决策分析」已被排除,首次 commit 不会包含子工程的流水账
