# 回流提案文档

> **本文件夹专门存放「回流提案文档」**——子工程整理好后，由用户带到母工程会话执行回流。

## 这是什么

当子工程开发过程中产生了**通用成果**（新工程纪律 / 通用工具骨架 / 通用踩坑经验 / 流程改进），
确认要回流模板母体时，子工程在这里产出一份**自包含的提案文档**，让母工程读了就能直接执行合并，
不需要回头了解子工程的业务细节。

## 完整流程

```
子工程                              用户                    母工程
  │ ① 识别候选(对照 reflux-signals) │                        │
  │ ② 记 REFLUX-CANDIDATES.md       │                        │
  │ ③ 收尾时确认回流,整理提案文档    │                        │
  │    落盘到本文件夹                │                        │
  │─────────────────────────────────▶│                        │
  │                                  │ ④ 用户带文档到母工程    │
  │                                  │───────────────────────▶│
  │                                  │                        │ ⑤ 母工程读文档执行合并
  │                                  │                        │   (评估纯度+去业务化+版本bump)
```

> ⚠️ **子工程不直接改母工程仓库**。职责分离让两边各司其职。
> 详见 `wiki/process/template-evolution-guide.md`「回流操作流程」。

## 提案文档怎么写（5 个必含字段）

新建 `<主题>.md`（如 `modularity-principle.md`），必含：

| 字段 | 内容 | 为什么需要 |
|------|------|-----------|
| **① 项目背景** | 这块改动是干嘛的、为什么这么改、解决什么问题 | 母工程不懂子工程业务，需要上下文判断该不该回流 |
| **② 改动原文** | 涉及的每个文件的**完整原文**（核心原则段 / §N.NN / §8 等所有层级）| 母工程不用跑去子工程翻文件，复制即用 |
| **③ 去业务化建议** | 提前标出哪些是业务专属引用（产品名 / 里程碑编号 / 特定案例）| 子工程最清楚自己的业务边界，提前标好省去母工程猜测 |
| **④ 纯度自评** | 自己判断"这个通用吗"：✅纯 / ⚠️部分通用 / ❌业务特有 | 给母工程做参考，母工程做最终裁定 |
| **⑤ 疑问/待确认项** | 拿不准的问题（如"这条要不要和现有 §1.X 合并"）| 留给母工程定，避免子工程拍错板 |

## 参考示例

clipboard-manager 的「模块化·高内聚低耦合」回流（模板 CHANGELOG [1.3.0]）就是一份合格的提案：
- 给了项目背景（大模型开发的复杂度控制）
- 给了 3 处改动原文（核心原则第 7 条 + §1.21 + §8 补充）
- 标出了业务引用（"M1 macOS / M3 Windows"）
- 自评了纯度
- 列出了 4 个疑问（回流规则在哪 / 标准流程 / 文件结构 / 纯度约定）

## 命名约定

`<主题>.md`，主题用简短英文 kebab-case（如 `modularity-principle.md`、`sidecar-removal-guide.md`）。
一次回流一个文件，不要把多个不相关的回流塞进同一个提案。
